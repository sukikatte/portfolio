HOK LINEUP AGENT

◆ A Draft Recommendation Agent for Honor of Kings ◆

Jan. 2026 - May 2026 · COMP47980 | Python · OpenAI Responses API · Function Calling · RAG · REST APIs
01

Project Overview

Honor of Kings is a 5v5 mobile MOBA. The high-stakes decision happens before the match starts: during the draft phase, players pick heroes from limited information — teammates, enemies, and their own assigned lane. A poor choice can leave the team with a weak frontline, no crowd control, or a losing lane matchup.

This project builds a technical draft coach that turns that lineup into lane-aware, evidence-grounded recommendations. Compared with vanilla ChatGPT, the assistant retrieves live Camp/KPL statistics, extracts official hero-detail pages, and reads curated local hero files inside a structured Responses API tool loop, so the pick is auditable rather than remembered.

02

Assistant Design

Tool-Grounded Agent Loop

The notebook implementation is powered by the OpenAI Responses API: multi-turn function calling, optional file-search retrieval, and retry/backoff for rate limits. Three tools expose the data layer — get_hero_camp_and_kpl_snapshot, get_qq_hero_detail_page, and get_hero_local_info — so each recommendation can cite Camp ranks, KPL presence, official hero text, and local tactics in the same pass.

The assistant also switches modes. In the default Top-3 replacement mode it proposes lane picks for an open slot. In locked-hero mode the user has already selected a hero, and the agent analyzes that hero against the same-lane opponent instead of generating a generic replacement list.

Design Constraints

Several choices keep the loop stable in a notebook setting. Parallel tool execution is disabled to avoid token spikes and keep the call trace readable. Code Interpreter is not part of the default main loop; a two-stage path can optionally append a structured ## NUMERIC TRACE without changing the recommendation itself.

Canonical name normalization, Camp/KPL cache maps, roster prefetch, and fallback parsing keep ~130 hero entries and three live endpoints usable inside one agent turn. Prompt consistency rules stop the model from claiming “no data” when numerical fields already exist.

03

Outside Knowledge

Detecting Official Files and API Calls

External game data was collected from official sources through browser developer tools and structured file extraction, then cleaned and connected for runtime use. The system mainly relies on three endpoints:

Official Hero Detail Page Endpoint — accessed through browser developer tools and network inspection, used for hero text extraction (pvp.qq.com/web201605/herodetail/).

Camp Hero Ranking API — internal endpoint for ranked hero statistics (api-camp.honorofkings.com/game/hero/getranklist).

KPL Hero List API — professional league statistics endpoint (prod.comp.smoba.qq.com/.../settle_list/open).

Static hero metadata and tactical text are stored locally to support retrieval and reduce repeated external requests. Data scale: approximately 130 hero entries from the full roster, plus a smaller curated subset of detailed profiles for RAG-style retrieval.

04

Worked Examples

The same draft question — “which hero should I play?” — is answered four ways: a ChatGPT baseline asked for data support, the agent with Code Interpreter and a numeric trace, the agent with Code Interpreter disabled, and locked-hero matchup mode.

Example 1 — Baseline Output from ChatGPT

Asked to “answer with related data support” for a Roam slot. The reply is detailed, but it does not actually include any official Camp, KPL, or hero-page data.

Example 2 — Agent with Numeric Trace

Same lineup, with detailed-numeric-explanation enabled. Code Interpreter jointly processes Camp data, KPL data, and heroes information. Top pick still Zhang Fei; the second and third alternatives differ from ChatGPT, and the tables make the ranking auditable.

Example 3 — Code Interpreter Disabled

The assistant still grounds the recommendation on retrieved and tool-fetched evidence, but skips the post-hoc numeric-trace stage. The response stays data-informed without extra trace-generation overhead.

Example 4 — Locked-Hero Mode

The user has already selected Zhen Ji. Instead of a Top-3 replacement list, the agent analyzes Zhen Ji versus Angela in mid: ranked and KPL evidence, lane matchup attributes, and play tips for that specific pairing.

05

Project Outcomes

The added value over a general chat response is structure for draft decisions, direct integration of live statistics and curated local files, and flexible runtime modes — with or without Code Interpreter, Top-3 replacement, or locked-hero matchup. Future work includes stronger alias resolution across endpoints, automated evaluation logs, and a more deterministic scoring layer for long-run consistency.

KEEP BURNING

◆ Unity 3D Corridor Runner ◆

Jan. 2026 - May 2026 | Unity · Blender · C#
01

Project Overview

Keep Burning is an endless corridor-style survival runner in Unity. The player controls a living flame moving forward through procedurally generated environments, managing fuel, avoiding hazards, and rescuing boys frozen into snowmen. The goal is to survive as long as possible while keeping the flame alive.

A continuous risk–reward loop drives the run: fuel decreases over time and is survival itself. Collecting fuel pickups and rescuing snowmen buy recovery. The narrative sits inside the mechanics — the flame is life and persistence, fuel is remaining time, and each rescue restores hope in a frozen world.

02

Core Loop

Keep Moving, Keep Burning

The flame auto-runs forward through an endless corridor. The player steers horizontally and jumps, dodging hazards across different map chunks while rescuing snowmen. Fuel drains continuously — it is live time, not a side meter. Pickups restore fuel; each successful rescue grants one extra life.

When the flame dies, one extra life is consumed and fuel is fully restored, so a saved life is a second run inside the same attempt rather than a game-over screen. Fuel intensity also maps onto the flame’s scale, color, and lighting, so remaining life is readable at a glance while running.

03

Fuel, Lives & Rewards

Fuel System

Fuel decreases for as long as the run continues and directly affects visual intensity. At zero the flame is extinguished unless an extra life is available. Collecting pickups is the short-term answer; extra lives are the long-term one.

Goals and Rewards

Rescuing snowmen awards extra lives and points. Points persist between runs: before a new game, players can spend them to buy an extra life, so a good run feeds the next attempt instead of resetting to zero.

04

Map, Hazards & Difficulty

Procedural Chunks

The corridor is assembled from a chunk-based procedural system, so each playthrough lays out differently. Ice surfaces add inertia and slower control response, turning the same input into a less obedient flame.

Hazards

Water extinguishes the flame. Obstacles interrupt movement and raise the cost of a mistimed jump. Moving out of bounds is immediate failure — the corridor is a track, not an open field.

05

Platforms & Next Steps

PC and Android

The same core loop ships on PC (macOS) and Android. The Android build is an APK with touch controls for movement and jumping; gameplay stays identical, only the input method changes.

Future Improvements

The design document sketches longer-term progression: Firebase Realtime Database for scores and live sync, a global leaderboard, and a buff / gacha layer for replayability — for example 3× score with reduced vision, 2× score with one life, or slower fuel decay.

06

Project Outcomes

Keep Burning folds avatar, timer, and tool into one flame. Movement, jump cost, fuel drain, hazard/pickup logic, extra lives, and procedural chunk spawning all speak the same resource language — readable without a cluttered HUD.

THE KEY

◆ Java Desktop Rhythm Game ◆

Jan. 2026 - May 2026 | Java · Swing · Java MIDI
01

Project Overview

The Key began as a shooting game and was redesigned into a rhythm-based music game: entertainment with educational value. Gameplay sits on the traditional five-line staff, so players recognise pitch positions and read basic notation rather than tapping anonymous lanes.

Two staves run at once — treble and bass. Two players can perform simultaneously, each controlling one staff, or a single player can take both registers. Live MIDI output makes the visual pitch audible, so a miss is a wrong note, not just a late tap.

02

Genre Transformation

From Shooter to Staff

Instead of shooting enemies, the player aligns with incoming musical marks and performs notes at the correct pitch and time. The original framework stayed; the core verbs changed.

The player character is a quarter-note symbol. The original shooting key (Space) became a mute key. Vertical movement changes pitch on the staff rather than aiming. Enemies were replaced by scrolling musical marks that indicate the required notes. Collision detection was replaced by a pitch–time matching window on a fixed performance line.

03

Game Modes

Free Compose

Continuous performance with no automatic ending — the player exits manually. The sequence of notes played on each staff is recorded and shown on the summary page, so the session reads back as a score rather than a replay of hits.

Song Performance

Prompt marks for Twinkle Twinkle Little Star scroll across the staff. Players perform the correct notes as closely as possible. The mode ends automatically when all marks leave the screen, and accuracy scores are displayed for both players — each register keeps independent scoring.

04

Music Theory & Piano Simulation

Two-Handed Play

Vertical pitch selection plus timed triggering simulates piano performance. Two-player mode maps onto two-hand playing: one person on treble, one on bass. Single-player two-staff mode raises the challenge by asking one person to cover both registers.

Notation Conventions

When the player mutes, displayed notes convert into rests rather than simply dropping the sound — silence is written, not just heard. Stem direction follows engraving rules: notes in the upper half of the staff take downward stems; notes in the lower half take upward stems. Stems stay visually centred and the staff keeps looking like real notation.

05

Implementation

Y-Position Mapping

Two staves are drawn first. The Y-coordinates of each staff line and the distance between lines set the spacing between semitone steps. Each pitch is a fixed Y-position; player movement is restricted to those discrete values. An index maps directly to both pitch and audio (MIDI note values in the Java implementation).

Scrolling marks are generated as indexed sequences. In Song Performance, scoring is calculated when a mark reaches the fixed performance line at approximately x = 700. If the player’s Y-position matches the incoming mark’s index inside the timing window, a score is awarded.

Treble Player

W / S — vertical pitch movement

Space — mute note

Bass Player

Up / Down — vertical pitch movement

Right Arrow — mute note

Global Controls & Materials

R quits the game; D opens the summary. Mouse input is used for menu interaction. All image assets were designed in ArtStudio; musical materials were recorded and generated in GarageBand. The system extends the original shooting-game framework in Java Swing without additional external libraries.

06

Project Outcomes

The Key treats the staff as the playfield, so pitch, timing, and reading stay coupled. MVC gameplay covers dual-player movement, mute/rest toggling, scrolling hit markers, and timing-and-pitch scoring, with notation-accurate feedback instead of a generic judgement line.

FRANKENSTORIES

◆ Story Generation from Reusable Parts ◆

Sept. 2025 - May 2026 · Grade: A | ComiXML · Python · OpenAI / Together APIs · LLM-as-a-Judge
01

Project Overview

Final Year Project at UCD, supervised by Prof. Tony Veale. Frankenstories asks whether large language models can generate novel comic narratives by recombining pre-existing parts inside ComiXML, rather than inventing unconstrained text and images.

The work implements a reproducible two-stage evaluation: first measuring structural reliability (XML well-formedness, schema validity, content validity, hallucination rate), then measuring narrative quality under factorial constraints with an LLM-as-a-judge protocol for continuity, coherence, and entertainment.

02

ComiXML as Constraint Interface

Machine-Readable Comics

ComiXML, developed by Prof. Veale, encodes a comic as a sequence of panels grounded in a finite library: characters, poses, settings, facings, and speech balloons. Visual choices are explicit tags, not free description, so outputs can be validated and reused across stories.

The library used in Stage One included 3 characters (Alfie, Betty, Gemma), 586 poses, and 149 settings. A generated panel that names a pose or setting outside that inventory cannot be rendered — which is why hallucination rate is treated as a first-class metric, not an afterthought.

03

Two-Stage Evaluation Framework

Why Two Stages

Structural failure invalidates narrative scoring: a comic that is not well-formed XML cannot be fairly judged for story quality. The framework therefore separates the two questions.

Stage One — Structural Reliability

Five models × two generation strategies × 20 narrative seeds = 200 ComiXML files. Method A uses staged planning-then-realization inside one call; Method B fills a ComiXML template in a single pass under explicit library constraints.

Result: Method B is the more reliable default. GPT-4.1 under Method B reached 96.8% content validity with a 3.2% hallucination rate, versus 80.2% / 19.8% under Method A. DeepSeek-V3.1 stayed near ceiling on both methods. XML well-formedness did not guarantee grounding: GPT-4.1 Method A produced 100% valid XML while still hallucinating nearly one fifth of elements.

Method B was therefore fixed for Stage Two, so later differences could be attributed to constraint load rather than prompt strategy.

Stage Two — Narrative Capability

The Frankenstories core: recombine one or more of 108 source-story packages with no seed text. A 2×2 factorial crosses cast complexity (single vs. multi-character) with source diversity (single vs. multi-source), from SC-SS to MC-MS. Five models × four conditions × five configurations × two replications = 200 files.

Claude Sonnet 4.6 scored each comic on local continuity, panel-level coherence, global continuity, and entertainment. Multi-source mixing stressed schema and grounding first; multi-character staging stressed panel control; MC-MS most clearly separated long-horizon narrative quality.

Tier 1: GPT-4.1 (strongest structural reliability) and DeepSeek-V3.1 (highest entertainment, competitive continuity). Llama-3.3 showed the weakest long-range continuity under high load.

04

Rendered Follow-up Comics

After diagnosing facing errors, missing characters mid-dialogue, and pragmatically wrong poses, the follow-up tightened staging constraints, added pose descriptions beyond name-level labels, and expanded the source bundle. Both outputs below remain valid ComiXML; the difference is how the recombination reads as a story.

GPT-4.1

More globally coherent arc: breakfast, the ride, the crash, hospital, lab, and return.

DeepSeek-R1

Structurally valid, with a more localized Frankenstories stitch: crash, serum, explosion, rebellion.

05

Project Outcomes

The thesis contributes a two-stage, reproducible evaluation workflow for ComiXML-based constrained generation, a tier-style consolidation for model choice, and practical guidelines: use Method B as the structural default, evaluate structure and narrative separately, and treat prompt control plus richer element semantics as the primary levers before switching models. Graded A.
